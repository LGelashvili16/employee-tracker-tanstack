# Jobs map

The jobs feature owns company-visible installation, measurement and other jobs with optional map coordinates. The generic `other` category is labeled `სხვა სამუშაო`, with a briefcase icon. All three categories share the same permissions, optional location, workflow and history. `/jobs` is the shared map/list workspace. Job creation and details open inside this workspace. Selected jobs use the validated `pin` search parameter. Redundant management/detail aliases and the separate new-job route have been deleted.

## Workflow and permissions

All active, authenticated company accounts can read pins. Claiming a pending task through `მივდივარ ობიექტზე` requires the separate `jobs.claim` permission, granted to production specialists, administrators and owners. Job-management permission alone does not permit claiming; sales managers, supervisors, operations managers and ordinary employees cannot use this action unless they also hold an eligible role. Claiming records the current account as the responsible person. Only that person or an account with `jobs.manage` can advance an active task. No client-provided assignee is accepted.

| Status      | Meaning                          | Next states                          |
| ----------- | -------------------------------- | ------------------------------------ |
| `pending`   | Unclaimed, planned work          | `en_route`; managers may also reject |
| `en_route`  | Responsible person is travelling | `on_site`, `rejected`                |
| `on_site`   | Responsible person has arrived   | `completed`, `rejected`              |
| `completed` | Work finished                    | Managers may reopen as `pending`     |
| `rejected`  | Work could not proceed           | Managers may reopen as `pending`     |

Managers may also return an active task to `pending`. Reopening removes its assignee. Rejection and reopening require a reason. Terminal jobs must be reopened before editing their location/instructions. A manager acting on a claimed task preserves its responsible person.

Production leads (`supervisor`, წარმოების უფროსი) and owners have job-management grants. Sales managers (`sales_manager`, გაყიდვების მენეჯერი) retain only `manage.access` and `jobs.manage` and are available in employee creation. The retired operations role is no longer available; migration `0026_consolidate_employee_roles.sql` preserves its existing access as individual permission exceptions. Administrators can read shared work and have the separate claim grant. Platform administration alone does not grant job management. An account can hold multiple roles.

The fixed `production_specialist` role is labeled `წარმოების სპეციალისტი` and is also available during employee provisioning. It can read shared jobs, claim pending work and progress its own work, but cannot create, edit, reopen or override other people's jobs. Like all roles, it is stored in the existing server-owned `user.roles` text column; no duplicate role table or new accounts are created.

Creation, edits and status changes record the authenticated actor's ID atomically in `job_event`. Detail reads resolve each actor's stored name and return the event timestamp, action, resulting status and any progress note. Client-supplied names/actor IDs cannot replace this attribution. The details summary shows the latest change's person and time immediately; the expandable history shows all returned edits and status changes with their authors. If recording an event fails, the associated job write rolls back. These permissions and presentation changes require no database migration.

## Job types and deadlines

Pins use type colors and matching icons: blue for installation, purple for measurement and neutral for other work. A separate corner badge shows the current status, including green completion and red rejection, without replacing the type's color. Both type and status appear in accessible marker names and the legend. Type badges use the same mapping in menus, details, cards and the list.

The editor's optional deadline uses the shared Georgian shadcn calendar. It can be set during creation, changed or explicitly cleared while editing. Deadlines are PostgreSQL `date` values returned as ISO calendar-day strings, never UTC instants; display and selection preserve the chosen day across device timezones. Past dates are allowed for historical work. Normal job editing permissions, terminal-state restrictions, version checks and atomic history still apply. Edits must explicitly supply a date or null so an old client cannot silently erase a newer deadline.

Context menus show the stored creator name and deadline, with an explicit empty state when no deadline exists. Details also show the deadline, and dated jobs include it in cards and the paginated list. Month/range filtering continues to use job creation dates. Migration `0015_job_deadline.sql` adds a nullable column and calendar bounds check; existing jobs remain undated. No reminder delivery or automatic status transition is implied by a deadline.

## Architecture and consistency

- `jobs.schemas.ts`, `jobs.rules.ts`, `jobs.types.ts` and `jobs.presentation.ts` contain client-safe validation, state transitions, contracts and Georgian labels.
- `jobs.functions.ts` validates and authenticates server calls. Services own workflows and transactions, policies reload current grants and account/employment state, and repositories own Drizzle queries.
- Writes lock current identity/employment and the job. Version checks prevent lost edits and concurrent claims. The mutation and its history entry commit atomically. A unique creator/request key makes creation retries idempotent.
- Conflicting dialogs preserve drafts, load the latest job for review, and require an explicit decision before retrying. A changed workflow can disable the requested action rather than silently overwriting another user's work.
- `job` and `job_event` retain completed and rejected work. New schema uses native PostgreSQL 18 UUIDv7. Apply the generated migration with the normal reviewed migration workflow.
- Query caches include actor identity. Search, status, category, responsibility, sort, page, view and selected pin are validated URL state. Lists filter/sort/page in SQL with stable tie breakers. Counts and rows share a repeatable-read snapshot.

## Map and UI

The jobs toolbar includes a shadcn range calendar for job creation dates in `Asia/Tbilisi`, matching job timestamp display. Missing date parameters resolve to the current full month; `/jobs` writes the validated `from` and `to` dates into the URL through a replacement redirect. Both endpoints are inclusive calendar days. The UI offers current/previous month shortcuts, month/year navigation, selection of the whole visible month and arbitrary valid ranges including a single day. Custom selections are drafts until Apply; Cancel does not change the URL. Date changes reset pagination and selected job details, and Reset restores the current month. Back/Forward restores the selected period.

The server validates both ISO dates, their order and calendar bounds. SQL uses an inclusive local start midnight and an exclusive midnight following the end date, converted with PostgreSQL's named timezone support. The same predicate scopes items, markers, matched counts and unlocated-job totals. Query keys and map job suggestions include the period; external address search remains independent. The existing creation-date index supports these comparisons without extracting dates from each stored timestamp. No schema migration is needed.

The shared `Map`, `useMap`, and `MapMarker` primitive is a focused adaptation of [mapcn](https://www.mapcn.dev/docs), retaining only the required map/marker composition. Teamwork's shadcn controls, Tabler icons and semantic badge tokens provide controls and status markers. No Lucide or competing UI library is added. MapLibre and its worker load in a separate browser chunk; Vite bundles the worker locally.

Basemaps use [OpenFreeMap](https://openfreemap.org/quick_start/) Liberty vector data with provider attribution. Light mode keeps Liberty's original colors. Dark mode uses the reference palette in `src/components/ui/map-styles.ts`: slate terrain, deep blue water, teal parks, subdued gray streets/buildings, and category-colored place labels. MapLibre's typed `transformStyle` applies it before the fetched style is committed, including initial load and theme changes, without mutating the light style or replacing its sources, fonts or attribution.

The dark palette was sampled from the user-provided map screenshot. Minor road cores appear at city overview zooms because the original daytime style otherwise relies on pale casings there. Daytime bitmap fills and low-zoom relief are suppressed to avoid leaking light colors; building footprints fade in with zoom. Geographic coverage, elevation shading, icon artwork and available places still follow the provider's data rather than Apple's map assets.

Tiles require internet access and no API key. Pin titles, instructions, assignees and history are rendered locally and are not sent to the basemap provider. Requests for tiles reveal the viewed map area to that provider.

Managers can right-click the canvas to choose installation, measurement or other work from a shadcn context menu. Its options, icons and creation labels use the shared kind schema/presentation mapping also used by the editor, filters, search results, cards and details. Touch long presses use the same menu; search/control/marker overlays cannot open it at stale coordinates. The header's new-job action opens the editor directly, even when WebGL or tiles are unavailable. Double-click keeps its normal zoom behavior. Details include progress notes, status controls and recent history; directions appear only for located jobs. All authored UI text is Georgian. Migration `0014_generic_job_kind.sql` expands the existing database check without changing saved categories.

The editor's exact-location shadcn switch is off for a new job opened from the header and on when started from a map location. Enabling it reveals the coordinate pair and requires both values. Disabling it saves both as null and removes any old marker and derived street names. Jobs without coordinates remain searchable, paginated and visible in the sidebar/list. The map reports their filtered count separately, and they never consume the 300-marker limit. Saving these jobs makes no geocoder request, so it does not depend on either map provider. Additive migration `0013_optional_job_coordinates.sql` preserves existing positions and enforces all-or-nothing coordinate pairs in PostgreSQL.

Opening a new job from the map context menu also previews its nearby address. A manager-only POST server function validates the Georgia coordinate pair and reuses the existing reverse lookup/cache. The editor prefers the Georgian label, then English. Reverse lookup requests up to five house/street candidates within 250 metres per language. It considers the nearest named match, refuses competing street names within a 15-metre distance gap, and retains a mapped house number only for a candidate within 30 metres without a similarly close conflicting number. Numbers always belong to the selected source feature; they are never borrowed from another building. Provider coordinates are representative points, so even these conservative matches remain approximations rather than verified building boundaries. Reverse cache version 2 prevents old street-only or empty results from masking the expanded lookup.

TanStack Form initializes the untouched address field while Query owns deduplication and loading. A compact info Alert asks users to verify the street and building number only while a new address remains automatically filled, including a search-selected address. It disappears after manual editing and is absent when editing existing saved addresses. Late results never replace a manually edited or cleared address, apply to changed/disabled coordinates, or alter a submission already in progress. Existing jobs and addresses supplied by search do not trigger another preview. A missing or ambiguous address, or provider failure, leaves manual entry and saving available with the orange warning Alert.

The map's maximize button opens a nearly full-screen shadcn dialog containing the same search, map, sidebar and editor workflows. Camera state survives expansion/collapse; explicitly selecting the same result again refocuses it. Search can collapse to an icon, while loading, empty and error states remain distinct.

Optional map places start hidden. The store-icon toggle restores POI symbols and labels, including shops, bus stops and airports. Street names, geography, job markers and metro stations/entrances stay visible. The OpenMapTiles `subway` and `subway_entrance` subclasses identify the metro exception; ordinary railway stations are not mistaken for metro stations. The setting survives map expansion and theme changes within the mounted workspace. It changes presentation only, without refetching job records or changing their filters.

Job markers have their own shadcn context menus with status, kind, title, address and responsible person. Details load through the existing authorized detail query only while the menu is open. Shared action rendering applies the same transition and edit rules as the detail panel. Every status change opens the existing confirmation dialog, including rejection/reopening reasons and version-conflict recovery; selecting a menu item never mutates a job immediately. Terminal jobs must be reopened before editing, and production specialists cannot edit or create jobs.

Both job markers and empty map locations support a deliberate one-second touch hold, right click and Shift+F10/context-menu keyboard access. Dragging beyond ten CSS pixels, lifting the finger, touch cancellation and additional fingers cancel a pending hold. The release click is suppressed after a successful hold. Map controls/search cannot start creation at an old coordinate, and a marker menu never opens the underlying location-creation menu. Ordinary taps still select a job, and map pan/pinch/zoom behavior remains available.

The map sidebar presents each result as a compact shadcn Card. Details show one useful address, the responsible person, nonempty notes and permitted actions. Duplicate derived street names, provider text and routine missing-data messages are omitted. The existing attribution remains on the map and address-search results. History remains available in a collapsed section, with timestamps identified as Tbilisi time.

Supplied coordinates must be inside Georgia's country polygon. The same territory check runs for context-menu creation, form coordinates, server-function inputs and direct service validation. Jobs may instead omit both coordinates. Existing records remain readable. The map can still be panned freely. See [boundary provenance and accuracy](../src/features/jobs/data/README.md).

Lists show 12 records per page. The map shows up to 300 matching pins with an explicit truncation notice; use filters and the paginated list to reach every record. Selecting a list record adds that pin to the map even if it falls outside the marker limit. The detail panel shows the latest 25 history entries; all older events remain persisted. Pins and selected details refresh every 30 seconds in visible tabs. This is polling, not live push, and arrival/completion are employee declarations rather than GPS verification.

## Address search and saved street names

The map has one collapsible search anchored inside the canvas. After a 500 ms typing pause, its shadcn popup groups addresses first and jobs of every supported kind below. Address lookup starts at three characters and job suggestions at two; no submit is required. Suggestions respect current job filters and keep the validated search text in the URL. Up to five jobs appear, with a link to the full list when there are more. Keyboard users can tab through results or press ArrowDown from the input to enter them.

Address lookup searches throughout Georgia even without an existing job. Selecting a result zooms to it and lets managers start a job there. Duplicate street segments with identical display names are collapsed. The shared SQL job filter searches saved text, including both street names and location labels. It appears as an ordinary search field only in list view, so map view has no second search bar. Query keys include actor identity and query/filter inputs; obsolete responses cannot replace a newer query, and repeated address queries reuse the client and server caches without background polling.

The server-only [Photon](https://github.com/komoot/photon) adapter uses OpenStreetMap data. Queries are requested in the local default language and English, then merged by source identity. The public demo does not support `lang=ka`; its default local names provide Georgian where present. Results must match country code `GE` and the same Georgia polygon used for pin validation. Public coverage, spelling and available translations vary. Missing names stay null; there is no automatic translation service.

On creation or coordinate changes, the server uses the same bounded address selection as the preview. It saves available Georgian/English street names and labels separately from the user's editable site address. Failed or ambiguous lookups never block saving, and moving a pin clears old names if the new lookup fails. Existing pins are not bulk backfilled; editing an unresolved pin attempts a lookup. Names remain historical metadata until its location changes.

Only the entered search text or coordinates are sent to Photon, never job notes or account details. Authorization is checked before lookup/cache access and rechecked in the job write transaction after outbound I/O. The adapter validates bounded responses, rejects redirects, uses an eight-second timeout, and makes no automatic retries. A database-backed gate spaces requests across app instances and bounds the waiting queue; normalized responses are cached for seven days with bounded expired-row cleanup. Unit and database tests stub the provider and never call the public service.

`GEOCODING_BASE_URL` selects a compatible Photon deployment; `GEOCODING_ENABLED=false` disables external lookups while preserving manual pin creation and saved-pin search. The default public Photon service allows reasonable use, may throttle heavy usage, and provides no uptime guarantee. It requires no key or paid account. Keep attribution to OpenStreetMap/Photon; consider a dedicated compatible deployment if traffic or availability requirements increase.

## Verification

`jobs.rules.test.ts` exercises permissions, ownership and state transitions. `jobs.schemas.test.ts` checks coordinates, reasons and malformed URL/input state. `jobs.integration.test.ts` creates an isolated local database, applies all migrations and checks authorization, races, idempotency, filters, audits and constraints. Run it with `RUN_JOBS_DB_TESTS=1` and a local PostgreSQL 18 `DATABASE_URL`; it never runs against a remote database.
