# Attendance security

Attendance uses Better Auth sessions and SimpleWebAuthn (`@simplewebauthn/server` 14.1.0 and `@simplewebauthn/browser` 14.0.0). Password sign-in is unchanged. WebAuthn is an additional check for an attendance action and never creates another login session.

## Controls and setup

- `/admin/settings/security` requires `security.configure`. Two switches control token verification and the additional Passkey check, using the existing server-side policy flags and preserving saved settings. Passkey requires token verification. Disabling token verification clears and disables the Passkey switch; re-enabling token verification leaves Passkey off. Company attendance IP rules and the application IP blocklist remain separate. Changes use an automatic audit description and reject stale revisions. Browser approval defaults to on and passkeys to off. When enabled, Passkey requires both checks without token-only fallback; both the service and database reject an inconsistent policy.
- For token-only attendance verification, enable browser approval and disable Passkeys. No employee-created keys or browser names are required. The protected app performs an authenticated POST after sign-in or a fresh application mount, issuing or reusing the HttpOnly browser cookie and identifying unknown browsers with state `unrequested`. Identification is audited without an HR notification or activation request. These inactive records are excluded from HR requests and device history but remain visible in the employee's current-browser summary. Reads and route preloads never create records. Repeated mounts reuse the existing browser, and signing in never restores a revoked device or resubmits an HR request automatically. Identification failure does not block the rest of the account; attendance still checks the current policy server-side.
- Every new browser, including the first, requires independent HR approval when that control is enabled. Approving another browser retains earlier approvals for that employee. Revocation takes effect on the next clock action. When browser approval and Passkeys are both disabled, browser records are retained for audit attribution, but approval status does not restrict attendance. Account status and IP checks still apply.
- `/settings/security` and the clock screen let an employee explicitly request browser activation. The `მოწყობილობის აქტივაციის მოთხოვნა` action moves an identified browser to pending HR review, records the request IP, and notifies reviewers once. Pending requests show a disabled `მოთხოვნა გაგზავნილია` button. Sign-in, navigation, page refresh, and clock preparation never submit activation requests. Existing approvals and pending requests are preserved.
- When Passkey is enabled, the clock screen offers `Passkey-ის დამატება` after activation is requested and the current browser lacks a key. Enrollment never clocks in/out, and registering a key on an already approved browser returns that browser to pending HR review. Rejected or revoked browsers explicitly request activation again, retaining an existing key instead of creating a duplicate. The existing reapplication cooldown and HR approval checks still apply.
- The management device table reads the active policy in the same transaction as its device list. Its Type column shows blue `Token`, purple `Token + Passkey`, or secondary `გამორთულია` according to the currently required verification. Saved credential presence is a separate column. Reactivating a browser retains an older key without making it mandatory in token-only mode. Starting and finishing Passkey enrollment each recheck the active server policy, so a stale page cannot enroll a key after the Passkey check is disabled.
- Automatic browser identification may run outside the attendance IP allowlist so normal sign-in remains available. The global blocked-IP list still denies it. Clock preparation and the actual clock-in/out transaction always recheck company and individual IP rules, regardless of browser-approval or Passkey switches. Explicit activation, reapplication, and Passkey enrollment also check the attendance network policy. Only accounts currently holding `admin` or `owner` are exempt from company and individual attendance allowlists. HR and all other roles still require an allowed address. Roles are read and locked from persistence, so stale or caller-supplied role claims cannot grant an exemption. Global blocked IPs, including fail-closed handling of unknown addresses when a blocklist exists, still apply to everyone. Browser approval and Passkey requirements remain unchanged.
- `/manage/devices` requires `attendance.devices.manage`. HR, administrators, and owners receive this explicit permission. The default view includes all requested device states, with URL-backed tabs for pending and active registrations and other statuses. Reviewers verify the employee through an independent channel, then approve or reject the specific registration. They can revoke an active browser. Decisions have no reason input and are audited with the actor, target, time, status change, and an automatic description. Rejected and revoked browsers can explicitly request review again after one minute.
- Admins, owners, and HR also receive `attendance.devices.approve.self`. Together with device-management permission, it permits explicit approval of their own pending browser through the normal confirmation dialog. The server rechecks persisted permissions and account/employment status, the pending state, revision, and any required saved Passkey. Own rejection and revocation remain prohibited. Self-approval is audited with actor and subject equal and `selfApproval: true`; it never disables clock IP or Passkey checks and never happens on sign-in. An unapproved browser can still access authorized device review, allowing the first privileged reviewer to activate their own requested browser without depending on another reviewer.
- Administrators can override an employee's attendance allowlist on their employee profile. Inheritance uses the company list; an explicit empty list denies attendance when IP restrictions are enabled. Global blocked IPs always win. Changing one's own individual network override is prohibited.
- Up to 20 pending or approved browsers per account are allowed. Revoke unused registrations before adding another. Previous registrations and their audit history are retained. Lists use server search, status filtering, sorting, and validated URL pagination.

Disabling the Passkey switch changes the next clock request. It does not approve a pending browser, restore a revoked browser, remove IP restrictions, suspend an account, or erase credentials/history. Existing approved browsers remain usable while a different browser awaits review.

## Hosting and trustworthy IP addresses

Set `BETTER_AUTH_URL` to the application's stable canonical origin. Production passkeys require HTTPS. Local `http://localhost:3005` works for development. Credentials are scoped to the configured relying-party hostname; changing the hostname needs a registration/recovery plan.

By default, request IPs come only from the runtime's direct peer address. Client-supplied forwarded headers are ignored. Some Nitro deployments do not expose a peer address to Start; in that case the address is unknown. IP-restricted attendance denies unknown addresses except for the Owner/Admin attendance allowlist exemption. An active global blocklist denies unknown addresses for every role.

When behind a controlled proxy, set `TEAM_ADWINGS_CLIENT_IP_HEADER=x-real-ip` or `TEAM_ADWINGS_CLIENT_IP_HEADER=cf-connecting-ip`. Only configure this after the proxy overwrites the chosen header and direct origin access is prevented. An environment switch cannot establish that network trust itself. `x-forwarded-for` is deliberately unsupported. Do not copy an incoming arbitrary header into the trusted header.

Enter exact public IPv4 or IPv6 addresses, one per line. CIDR ranges, hostnames, ports, and comma-separated forwarded chains are not individual IP entries. IPv6 and IPv4-mapped IPv6 addresses are normalized before comparison. Company devices behind NAT may share one public address. A VPN/proxy or remote access to an office computer can undermine location assumptions.

Blocked IPs are denied at the global Start request middleware, including authenticated application/server-function and Better Auth requests. Existing SSE connections recheck the blocklist before sending events and at their next heartbeat, at most 25 seconds later. If a blocklist exists and the address cannot be established, access fails closed. Policy saves prevent adding the administrator's current address to the global blocklist. Other reviewers behind the same public address can also be affected. Public assets served directly by a CDN/Nitro static handler are outside Start: configure corresponding edge restrictions if those must also be inaccessible. Never rely on public asset secrecy.

If a deployment changes address/proxy configuration and locks out access, a trusted database operator can remove the erroneous blocked address in `attendance_security_policy`, recording the maintenance reason through the operational change process. There is no hidden browser bypass or administrator URL exception.

## Action authorization and attribution

Every clock action checks the current active account, approved browser cookie, configured networks, and current passkey policy on the server. A random 256-bit persistent HttpOnly browser cookie is stored as a SHA-256 hash server-side, independently for each account using that browser. It has a one-year browser lifetime and matching server-side maximum registration age. Secure production cookies use the `__Host-` prefix. Clearing cookies or using another browser requires registration again. This is browser registration, not proof of a unique physical device. Synced passkeys may exist on multiple authenticators.

WebAuthn challenges expire after two minutes. They are bound to the current actor, login session, browser, operation kind, validated payload, target employee, and HR reason. Verification checks the expected origin, RP ID, signature, counter, and user verification. Challenge consumption, attendance changes, punch attribution, and required notifications share one database transaction. Competing actions serialize on the approved device and employee; existing attendance overlap, active-employment, schedule, nonworking-day confirmation, and stale-state protections remain in force.

Challenge creation is serialized and limited to 10 outstanding recent challenges per account per minute. Registration requests are deduplicated per account/browser; denied clock events are journaled with a maximum of 20 entries per actor per minute. Credentials, cookie values, and assertions are never written into audit details or returned by device-list reads.

`attendance_punch` records the attendance employee, subject account, actual acting account, in/out kind, employee/HR source, authoritative effective time, database recording time, acting IP, approved browser, credential reference, verification result, and HR reason. The clock-in and clock-out actors can differ. Corrections preserve these original punch facts and use the existing append-only before/after correction audit. Historical sessions without punch attribution are labeled as historical instead of inventing an actor. Automatic closures remain identified by `auto_closed_at` and display the system as the source when no human checkout punch exists.

When attendance IP restrictions are enabled, each successful Owner/Admin clock action also writes `clock.ip_allowlist_exempted` to `attendance_security_audit` in the same transaction as its punch. The entry retains the acting account, attendance session, subject account, in/out kind, actual IP (or null when unavailable), exempt role, policy revision, and database timestamp. Failed and idempotently repeated punches do not create successful exemption entries. The exemption concerns the acting account, including an assisted punch; it never transfers that role to the subject employee.

## HR-assisted attendance

`attendance.clock.assist` is granted explicitly to HR, administrators, and owners. It allows acting for another active employee through their management attendance page. Self-assistance and client-supplied role claims are rejected. HR uses their own approved browser, applicable IP rules, and passkey when the extra check is enabled. The employee's broken/revoked browser is not needed and is not silently approved. A reason and explicit confirmation are required; the employee receives a notification.

Assisted actions record the server's current time. Restoring an earlier worked time remains a separate correction workflow, with its own permission, reason, original values, and audit history. Approval of a device never creates or backdates attendance. Global account suspension and blocked-IP restrictions remain independent.

## Verification

Device management shows the account that made each device's latest approval, rejection, or revocation and its recorded decision time in the company timezone. This reads the existing `reviewed_by` and `reviewed_at` fields; the employee requesting activation remains a separate column. Reapplication clears the current decision fields while retaining earlier decisions in the audit history.

Migrations `0033_attendance_security` and `0034_attendance_security_constraints` preserve existing sessions and attendance. Apply them before running the changed server. Neither migration fabricates approvals or historical punch attribution.

Run `pnpm exec tsc --noEmit`, `pnpm test`, and `pnpm build`. Run the isolated PostgreSQL suites with:

```powershell
$env:RUN_ATTENDANCE_SECURITY_DB_TESTS='1'
$env:RUN_ATTENDANCE_DB_TESTS='1'
pnpm test src/features/attendance-security/server/attendance-security.integration.test.ts src/features/attendance/server/attendance.integration.test.ts
```

The security suite creates genuine ES256 registration and authentication responses and exercises the real SimpleWebAuthn verifier. It covers session/action binding, replay, missing verification, wrong origins, expiration, revocation, network rules, policy disabling, actor attribution, permission spoofing, and competing punches. Tests require local PostgreSQL and create/drop only randomly named test databases.
