# Business notifications

Business workflows call `deliverNotifications` from their existing transaction. Domain writes, audits, persisted inbox rows and PostgreSQL live signals commit or roll back together. Delivery removes the actor, duplicate recipients and inactive/suspended accounts. An employee record must be active when present. Event identity plus recipient is unique; retries of stale revisions cannot generate another notification.

| Employee cancellation                                        | Current authorized leave reviewers with management access                            | Generic cancellation and dates, reviewer request filter                                              | Request ID, saved revision, cancelled              |
| Employee closes sick leave                                   | Current authorized leave reviewers with management access                            | Generic absence closure and final dates, reviewer request filter                                     | Request ID, saved revision, closed                 |
| Reviewer closes sick leave                                   | Requester                                                                            | Generic absence closure and final dates, own request filter                                          | Request ID, saved revision, closed                 |

Leave reviewer candidates are selected in bounded keyset pages from current role grants or explicit permission allows, then checked with the central current authorization parser including denies and management access required by the reviewer destination. Job notifications never broadcast to unrelated managers or every potential claimant. Large company deliveries use bounded recipient pages with the same event identity.

Leave notifications never copy an employee's note or medical detail. Repeated unchanged leave dates are rejected by the existing workflow. Unchanged individual effective hours, company hours and job material fields do not notify. Initial individual schedule provisioning does not notify. Existing open attendance sessions keep their captured expected times. Unchanged attendance punches preserve the revision and prior review state.

## Live behavior

Jobs register their own feature handler on the shared `/api/events` connection. Every committed create, edit and transition wakes authorized workspaces; initial/reconnect snapshots reconcile all active list/detail queries. List/detail periodic polling is removed. The handler rechecks current account, employment and workspace access and sends no job content. Availability never shows a toast.

Generic notification events refresh the inbox through its own hook. Application composition also refreshes the affected actor's open leave, own schedule, attendance and timesheet queries. Reconnect snapshots reconcile these caches without replaying historical notifications. Attendance retains its normal clock/day refresh because ordinary clock-in/out are not persistent notification events. Existing announcement and complaint hooks own their records, unread feature state and toasts; only the notification hook owns inbox live invalidation.

No notification is emitted to reviewers on every checkout. A committed notification persists while the user is offline; transient live signals reconcile via reconnect snapshots.

## Scheduled attendance notifications

| Event                  | Recipients and timing                                                                                                                                                                                                                                                                              |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Start reminder         | Active employee on the effective company or individual working day, at start minus the configured minutes (zero means at start). Skip approved absence, already recorded attendance for that date, any open session, and expired working hours. Tomorrow's early start may be due before midnight. |
| Finish reminder        | Employee with an open session, at the captured expected end minus the minutes from its original schedule version. A confirmed nonworking session with equal expected endpoints has no finish reminder.                                                                                             |
| Excessive open session | Employee and currently assigned authorized reviewers when elapsed time reaches the captured maximum. After midnight the link still uses the original work date. Closing the session prevents new reminders. Previous notifications stay in the inbox.                                              |
| Pending review digest  | Assigned reviewers with active employment, management access, attendance read and review rights. After expected end or on a past work date, send a quiet inbox entry grouping one employee's pending records for that work date. Never send self-review notices.                                   |

Nitro starts the minute schedule automatically with the Vite development server and deployed Node server. There is no task HTTP endpoint. Deploy the generated migrations before starting the new release. At least one process must be running; there is no external queue, push notification, email or automatic checkout. At startup the next tick considers still eligible work, not expired reminders. Nitro disables cron when its TEST environment switch is set.

Each category selects up to 64 undelivered recipient records per tick. A PostgreSQL transaction advisory lock serializes replicas, and inbox uniqueness plus per-reviewer session revision receipts survive restarts. Selection, receipts, inbox inserts and identifier-only live signals commit together. A timeout or serialization failure rolls back the tick and retries on the next minute. Current assignments get outstanding pending work, and later corrections can generate a new entry even after the old digest was read. A group gets at most one digest per UTC clock hour: subsequent changes in that hour are picked up in the next hour, normally within 61 minutes of eligibility. Outages and batches larger than the per-tick cap can extend that delay.

The bell toolbar explicitly marks the account's entire unread inbox read, including entries outside the five-item preview and older pages. The server derives the recipient from the session and updates read state atomically; existing notification and complaint SSE signals synchronize the bell and management dot. Individual row controls still affect only their own entry.
